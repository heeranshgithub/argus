One endpoint, two sides of a line

POST /api/sessions/{id}/run answers in milliseconds and then runs a 30–90 second LangGraph workflow on the same worker. Everything confusing about this endpoint comes from not knowing exactly where that line falls. This page puts it under a microscope: every gate before the 202, the precise Starlette mechanic that defers the work, and what it costs you.

Start here

The problem, stated precisely

The workflow is six LLM-backed graph nodes with a research loop. Every node makes network calls. A full run is a minute or more. A POST cannot sit on that.

Holding the connection open for ninety seconds fails three ways: proxies and load balancers time it out, a refresh orphans the work with no way to find it again, and the browser has nothing to render in the meantime. But you also cannot just fire-and-forget — the client needs a handle on the work it just started.

The contract we need

The POST must return immediately with an identifier that already exists and is already queryable, and the actual work must start after that response is on the wire. Progress travels on a different connection entirely.

That is the async request-reply pattern, and naming it is worth doing out loud. 202 Accepted is the status code that means exactly this: I have taken responsibility for this work, here is where to watch it, I am not going to do it while you wait.

The core idea

The whole split in one picture

Two things become free at two different moments, and conflating them is the single biggest source of confusion here.

The green half runs while the browser is blocked on the POST; the gold half runs after it has already been answered. Both sit inside one ASGI call — which is why that request's coroutine stays alive long after the client is free. The event loop is not blocked: every await inside the graph yields, so other requests are served normally throughout.

The one sentence to remember

The client is released when the response body is sent. The worker is released only when the background coroutine finishes. Those are minutes apart, and the POST's own latency log only measures the first one.

Progress never travels on the POST. The two connections share exactly one thing: the runId.

The ordering rule

Why start() must precede add_task

async def start_run(db, deps, session_id, background_tasks) -> RunAccepted:
    await session_service.get_session(db, session_id)   # raises SessionNotFound
    if await workflow_repo.has_active_run(db, session_id):
        raise SessionAlreadyRunning(session_id)

    runner = WorkflowRunner(db, deps)
    run_id = await runner.start(session_id)                # ① writes to Mongo NOW
    background_tasks.add_task(runner.execute, run_id, session_id)  # ② queues only
    return RunAccepted(run_id=run_id, status=RunStatus.RUNNING)
The reason the runner has two methods

The instant the client holds a runId it fires GET /runs/{runId} for first paint and GET /runs/{runId}/events for the stream. Both call get_run, which raises RunNotFound on a missing document. Schedule first and you hand out an id that 404s. So start() is the synchronous prep that must be durable before you answer, and execute() is everything that may take a minute.

This generalizes: in any async request-reply endpoint, the receipt must be committed before it is handed out. The 202 body is a promise, and a promise referencing a row that does not exist yet is a lie you will debug at 2am.

The mechanism

What add_task actually does

It does not start anything. It appends a BackgroundTask(func, *args) to a list. That is the whole method.

FastAPI attaches that list to the Response object it builds from your return value. Starlette's Response.__call__ then does three things in strict order:

Why this is possible: send() is not return

ASGI is a calling convention between the server and your app. The entire application is one async callable, and uvicorn invokes it exactly once per HTTP request:

async def app(scope, receive, send) -> None: ...
#   scope   — request metadata (method, path, headers)
#   receive — await it to pull messages FROM the client
#   send    — await it to push messages TO the client

# uvicorn, once per request (httptools_impl.py):
result = await app(self.scope, self.receive, self.send)

Look at the return type: None. The response is not the return value. It is pushed out through send() as messages, in the middle of the call — which is exactly what Starlette does:

# starlette/responses.py — Response.__call__
await send({"type": "http.response.start", "status": self.status_code, ...})
await send({"type": "http.response.body", "body": self.body})   ← client is done

if self.background is not None:
    await self.background()                                  ← the graph, still inside app()
Sending the response ≠ finishing the call

These are two separate events, and BackgroundTasks lives in the gap between them. Once the body message is sent the client has its 202 and hangs up — but await app(...) has not returned, so every stack frame that led here is still on the stack while your ninety-second workflow runs.

Which middleware is still on the stack

Starlette's add_middleware inserts at the front of the list and the stack is built in reverse, so the last one added ends up outermost — that is why main.py adds RequestIDMiddleware last. The full onion for a run request:

uvicorn  ──  await app(scope, receive, send)
└─ ServerErrorMiddleware         (Starlette, always outermost)
   └─ RequestIDMiddleware        (ours: request_id, latency, metrics)
      └─ SlowAPIMiddleware       (the 5/min rate limit)
         └─ CORSMiddleware
            └─ ExceptionMiddleware   (our domain errors → 404 / 409 / 503)
               └─ APIRouter → start_run() → Response.__call__
                                              ├─ send(http.response.start)
                                              ├─ send(http.response.body)   ← client free
                                              └─ await background()         ← the graph runs HERE

Every one of those frames is still live while graph.ainvoke runs. That is not a leak — it is the mechanism.

In-process deferred coroutine, not a job queue

The graph starts after the client holds the complete 202 — but inside the same ASGI call, on the same event loop, in the same process. BackgroundTasks is Starlette's after-response hook. It has no persistence, no retry, and no redelivery.

Because execute is async, Starlette awaits it and every LLM / search / Mongo await yields control — other requests keep being served. You are deferring work, not blocking a thread.

Consequences

Three things that bite

1 · Latency logs lie

RequestIDMiddleware is a BaseHTTPMiddleware, so call_next returns as soon as the response starts. Its request_completed line records single-digit milliseconds for a POST whose worker is then busy for a minute. The number is real; it is just not the cost of the request.

2 · The log context survives the crossing

The background task runs in a context copied at task creation, so structlog's request_id is still bound inside execute.

Measured, not assumed

I probed this directly against the app: the request_id visible inside the background task is byte-identical to the X-Request-ID header on the response. So planner_done, run_completed, run_failed — every line the graph emits for the next ninety seconds — carries the same request id as the 202 that started it. That is your grep key across the whole run.

3 · The runner object stays alive on purpose

add_task(runner.execute, …) stores a bound method, so runner and its db stay referenced for the duration. This is safe only because runner.db is the process-wide Motor handle. If get_db yielded a per-request session that closed when the response was sent — the way a SQLAlchemy session dependency normally does — this exact code would explode on the first query after the 202.

Classic interview trap

"Can I use my request-scoped DB session inside a background task?" No. The response is already sent, so any resource tied to the request lifecycle is closed or closing. Either use a process-wide handle (what Argus does) or open a fresh session inside the task.

The background half

execute() and the ContextVar

async def execute(self, run_id, session_id, *, resume=False) -> None:
    ctx = RunContext(
        db=self.db, run_id=run_id, session_id=session_id,
        bus=event_bus, cost_cap_usd=self.settings.workflow_max_cost_usd,
    )
    cost_token = llm_tool.set_cost_reporter(ctx.record_cost)
    async with bind_run_context(ctx):            # ContextVar, NOT GraphState
        await emit(EventKind.RUN_STARTED, node=RUN_NODE, payload={"resume": resume})
        try:
            final_state = await self._invoke(run_id, session_id, resume=resume)
        except Exception as exc:
            await self._fail(run_id, session_id, exc)
            return
        finally:
            llm_tool.reset_cost_reporter(cost_token)
        await self._complete(run_id, session_id, final_state)
Why a ContextVar and not the graph state

Nodes need a db handle, the run id, the seq counter and the event bus. None of those can live in GraphState, because the state is msgpack-serialized into the Mongo checkpointer after every super-step — a Motor client or an asyncio.Queue in there is unserializable. So live handles ride a ContextVar. ainvoke copies the current context into each node task, which is exactly why binding it just before invocation makes it visible in all six nodes.

The one config line that makes resume possible

config = {
    "configurable": {"thread_id": session_id},   # NOT run_id
    "recursion_limit": self.settings.workflow_recursion_limit,   # 30
}

if resume:
    return await graph.ainvoke(None, config=config)   # None ⇒ load last checkpoint

thread_id is the session id, not the run id. A resume creates a brand-new run document but reuses the same thread, so LangGraph finds the previous run's checkpoints and continues from the last completed node instead of starting over.

Two subtleties worth naming out loud

It loops to the planner, not the researcher. The researcher already has every question in researched_question_ids, so returning to it would re-run the same plan and fetch nothing new. The planner reads quality.missing_areas and appends sharper gap-closing questions.

The empty-missing_areas guard is load-bearing. The schema permits needs_more_research=true with no listed gaps — without a target the planner would just regenerate its original questions and spin until the iteration cap.

Every node body is wrapped in async with emit_node(name), which brackets the work with node_started on entry and node_finished (with a preview and duration_ms) on clean exit. On exception it emits node_errored carrying only a sanitized code and re-raises, letting LangGraph's RetryPolicy take over for transient transport errors.

Guardrail

The cost cap is enforced between nodes

set_cost_reporter routes every LLM call's cost into ctx.record_cost, which accumulates and flips a cost_exceeded flag — and deliberately never raises.

Why the accumulator can't raise

It is called from inside the retrying LLM client. An exception there would be caught by the retry wrapper and trigger more calls — you would spend more money detecting that you had spent too much. So the check happens at the node boundary instead: after node_finished is emitted, an exceeded cap raises CostCapExceeded. The run fails cleanly after the over-budget node rather than thrashing inside it.

Default cap is $1.00 per run, and the resulting failure is classified retryable: false — resuming would immediately re-trip the same cap, so the UI does not offer a Resume button.

Bookkeeping

How a run ends

_complete stamps finished_at, records final_state_keys, and persists raw_sources onto the run document — so follow-up chat can rank over the fetched sources without re-reading LangGraph checkpoint blobs. Then session → completed, metric, run_completed event.

_fail is the last line of defence, and it is written like one

The bug this design exists to prevent

If the failure handler itself raises, the run is stranded as running forever and the UI streams an event that never arrives. So every step is total or guarded: classification cannot throw, persistence sits in a try, and the run_failed emit is wrapped in contextlib.suppress inside the finally. A stream that ends badly beats one that hangs.

Nothing from the exception's text reaches the browser

classify() maps the exception to a fixed Failure: a stable code the frontend branches on, a written-for-humans message, and retryable. The raw text and traceback go to error_detail on the run document — a key no API model reads — and to the log line.

Why this matters concretely

OpenRouter answers a bad API key with "User not found". Surfaced verbatim, a user reads that as their own account being gone. Provider error strings are written for the developer holding the key, not for the person waiting on a report — so classification happens once, at the boundary.

Fan-out

One emit, two sinks, one seq

Every node transition calls emit(), which does exactly two things in order.

  1. Durable, always. An atomic $push onto workflow_runs.events, optionally also $setting node_status.<node> in the same update_one. Mongo is the source of truth.
  2. Best effort, in-process. A publish to the EventBus. If nobody is subscribed it is a no-op — and the event has already landed in Mongo, so nothing is lost.

The seq is a plain integer on the RunContext, monotonic from 1. It is the join key for the entire streaming story: backfill replays seq > since_seq, the live loop drops anything at or below it, and the client de-duplicates by it. The SSE deep dive covers that half in full.

Backpressure without blocking the producer

Subscriber queues are bounded at 512. On overflow the bus evicts the oldest event and bumps a counter — a stalled browser tab can never block the workflow. Dropped events stay recoverable from Mongo via since_seq.

Know these cold

Sharp edges

None of these are bugs in the code as written. They are the consequences of choosing an in-process deferred coroutine over a job queue — and being able to name them unprompted is the difference between "I used BackgroundTasks" and "I chose BackgroundTasks."

It is not a job queue

Same process, same event loop, no persistence in the task object. Kill uvicorn mid-run and the graph simply stops — no retry, no redelivery, no other machine picking it up. What makes the work recoverable is the Mongo checkpointer plus the lifespan handler that flips still-running sessions to interrupted on graceful shutdown. Not BackgroundTasks.

A hard kill strands the run row, not the session

An asymmetry worth knowing before you debug it

mark_running_interrupted updates the sessions collection only. After a crash (or any exit that skips lifespan), the workflow_runs document stays running forever, so has_active_run keeps returning true and POST /run 409s permanently on that session — while POST /run/resume still works, because it checks session status instead.

Two workers split the live stream

The EventBus is a module-level object in one process. With more than one uvicorn worker, the POST may run the graph on worker A while the SSE connection lands on worker B, which sees no live events at all. Mongo backfill still works, so the UI paints correctly on refresh but never streams. This is a liveness limitation, not a correctness one — and the 409 guard survives, because it is a database read. Redis pub/sub or a real queue (ARQ/Celery) is the fix; it is called out as future work, not built.

The 409 guard is check-then-act

has_active_run and create_run are two round-trips with no transaction and no unique index between them. Two simultaneous POSTs can both read "no active run" and both insert. The window is small and the rate limiter narrows it, but it is open — the durable fix is a partial unique index on (session_id, status="running").

In-process tests run the background before the POST returns

Measured — and it inverts the obvious assumption

httpx's ASGITransport awaits app(scope, receive, send) to completion, and that call does not return until the background task finishes. I probed it against the repo's own fixtures: a GET issued immediately after the POST returned status=completed, events=15 — the entire graph had already run. So a test asserting "still running right after the POST" would be asserting the opposite of what happens. Under real uvicorn the client genuinely does get its 202 first.

A client that hangs up does not cancel the work

Nothing checks for disconnect on the POST side. Close the tab a second after the 202 and the full run still executes, spends its LLM budget, and writes its report. Only the SSE handler watches request.is_disconnected(), and that ends the stream, not the run.

The sibling endpoint

Resume, and why chat does it differently

POST /run/resume is structurally identical: validate, create a new run row, add_task(runner.execute, …, resume=True), 202. Only the guard differs — it requires the session to be failed or interrupted rather than requiring no active run. All the continuity comes from thread_id == session_id in the checkpointer.

Why the difference is deliberate

The workflow's prep must be committed before the 202 body can honestly contain a runId, and the after-response slot is a defined point — no orphan task racing the response on its way out. A chat reply has no such receipt to commit and is short-lived, so a truly detached task with an in-memory buffer is the cheaper fit.

Flashcards

Rapid-fire

Why 202 and not 200 or 201?

202 Accepted means "I've taken responsibility for this work but haven't finished it." 200 would imply the result is in the body; 201 would imply a resource was created at a location you can now GET as the finished thing. The run is created — but what the client gets is a handle to watch, not the outcome. 202 is the honest code for async request-reply.

Does the request finish before the background task runs?

The response does; the ASGI call does not. Starlette sends http.response.start and http.response.body, then awaits the background task. So the client is released immediately, but the coroutine handling that connection stays alive until the graph finishes. That is why the POST's logged latency is milliseconds while the run is still going ninety seconds later. The loop is not blocked, though — every await in the graph yields, so other requests are served the whole time.

Why must the run row be created before add_task?

Because the 202 body hands the client a runId it will immediately use for GET /runs/{id} and the SSE stream — both of which 404 on a missing document. Committing the receipt before handing it out is the general rule for async request-reply.

Can you use a request-scoped DB session in a background task?

No. The response is already sent, so anything tied to the request lifecycle is closed or closing. Argus gets away with it because get_db returns the process-wide Motor handle off app.state, not a per-request connection. With a typical SQLAlchemy session dependency you would open a fresh session inside the task instead.

Why not just use Celery or ARQ?

You should, for a real deployment — and I'd say so. BackgroundTasks buys simplicity: no broker, no worker fleet, no serialization boundary. What it costs is durability (a kill loses the in-flight run), multi-worker fan-out (the live event bus is in-process), and isolation (a heavy run competes with request handling on the same loop). Argus mitigates the first with the Mongo checkpointer plus resume, and documents the second as a known limit.

What stops two runs racing on the same session?

has_active_run — a projected find_one for a running run — returns 409 before anything is created. Without it, two POSTs would queue two executes against the same thread_id and interleave their checkpoint writes. It is check-then-act though, so two truly simultaneous requests can both pass; a partial unique index on (session_id, status="running") would make it airtight.

How does a crashed run become resumable?

Two pieces. The checkpointer snapshots graph state to Mongo after every super-step, keyed by thread_id = session_id. The lifespan handler flips any still-running session to interrupted on graceful shutdown, which is a state resume_run accepts. Resume then creates a new run row and calls ainvoke(None, config) — passing None tells LangGraph to load the last checkpoint rather than start fresh.

Why is the cost cap checked between nodes instead of inside the LLM client?

Because the accumulator runs inside the retrying client. Raising there would be caught by the retry wrapper and trigger further calls — you'd spend more money detecting overspend. So record_cost only sets a flag, and emit_node raises CostCapExceeded at the node boundary after node_finished. The run dies cleanly instead of thrashing.

Why doesn't the client ever see the real exception?

Provider errors are written for the developer holding the API key. OpenRouter answers a bad key with "User not found", which a user reads as their account being gone — misleading, and it discloses infrastructure on a public endpoint. So classify() maps the exception to a stable code, a human message, and a retryable flag; the raw text and traceback go to error_detail (which no API model reads) and the logs.

Inside the researcher node

The only node in the graph that never calls an LLM. It turns a list of questions into a de-duplicated corpus of cleaned page text — through a search API it does not control, over a network that fails constantly, under a concurrency budget and a byte cap. This is the node where everything that can go wrong, does, and the design is mostly about degrading instead of dying.

What this node is actually for

Every other node is a prompt with a schema. This one is an I/O pipeline: it is the only place Argus touches the open internet, and the only node whose failures are expected rather than exceptional.

Its contract is narrow. In: the sub-questions the planner produced that have not been researched yet. Out: an append to raw_sources, an increment of research_iteration, and a record of which question ids are now done.

{
  "raw_sources": [...],              # reducer channel — appended, deduped by url
  "research_iteration": iteration + 1,
  "researched_question_ids": [q["id"] for q in todo],   # also a reducer
  "errors": errors,                  # only when non-empty
}
Why researched_question_ids exists

It is what makes the research loop cheap. On a second pass the node filters todo to questions it has not seen, so a loop-back only chases the planner’s new gap-closing questions instead of re-searching the whole plan. It is also the reason the conditional edge loops back to the planner and not straight to the researcher — re-entering the researcher with no new questions would produce an empty todo and fetch nothing.

The shape

Fan out wide, squeeze through a narrow gate

Every question is searched in parallel, every search produces several hits, and every hit wants an HTTP request. Left alone that is an unbounded burst against the network. The whole node is shaped by one constraint: a semaphore that lets only four fetches run at once.

Two levels of asyncio.gather — one over questions, one over each question’s hits — feeding a single shared semaphore.

Stage 1

Search: a protocol with two implementations

The node never imports a search vendor. It depends on a Protocol — Python’s structural typing, closest to a TypeScript interface — and whatever satisfies it gets injected.

@runtime_checkable
class SearchClient(Protocol):
    async def search(self, query: str, k: int = 5) -> list[SearchHit]: ...

class SearchHit(TypedDict):
    url: str
    title: str
    snippet: str

Three things implement it: TavilyClient (primary, an LLM-oriented search API returning clean JSON), DuckDuckGoClient (key-free fallback that POSTs to the HTML endpoint and parses the result list with BeautifulSoup), and FakeSearchClient in the tests. Selection happens once at startup:

def build_search_client(settings) -> SearchClient:
    if settings.search_provider == "tavily" and settings.tavily_api_key:
        return TavilyClient(settings.tavily_api_key)
    return DuckDuckGoClient(timeout_seconds=settings.fetch_timeout_seconds)
Why a Protocol rather than a base class

Nothing has to inherit anything. A class is a SearchClient if it has a matching search method — so the fake in the test suite is not coupled to the real one, and swapping vendors touches one factory function. This is the same dependency-inversion move as WorkflowDeps itself: nodes depend on capabilities, never on concrete clients.

Retries live in the client, not the node

_search_retry = retry(
    retry=retry_if_exception_type((httpx.HTTPError, ConnectionError, TimeoutError)),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=1, max=4),
    reraise=True,
)

Both clients wear this tenacity decorator: three attempts, exponential backoff, and only for transport errors — a malformed response or an auth failure is not retried, because it will not fix itself. reraise=True means the caller sees the original exception rather than tenacity’s wrapper, which matters because the node’s error record stores str(exc).

Retries nest three deep here

A single failing search can be attempted 3× inside the client, and the whole researcher node can be retried 2× by LangGraph’s RetryPolicy. Worst case that is six search calls for one question. Bounded, but worth knowing before you widen either number.

Stage 2

Fetch: three guards around one GET

Fetching an arbitrary URL from the open web is the most hostile thing this app does. HttpxFetcher wraps it in three limits.

async with httpx.AsyncClient(
    timeout=self._timeout,           # 1. 8 seconds, whole request
    follow_redirects=True,
    headers={"User-Agent": _USER_AGENT, "Accept": "text/html,*/*"},
) as client, client.stream("GET", url) as resp:   # 2. streamed, not buffered
    resp.raise_for_status()
    body = await self._read_capped(resp)                   # 3. stop at 1 MB
  1. Timeout. Eight seconds for the whole request. Without it one slow host stalls a semaphore slot indefinitely and starves every queued fetch behind it.
  2. Streaming. client.stream rather than a plain get, so bytes arrive in chunks and the cap can be enforced while downloading — not after a 400 MB response has already landed in memory.
  3. Byte cap. _read_capped accumulates chunks and breaks the moment it crosses 1 MB. Truncating mid-document is fine: the cleaner only wants prose, and 1 MB of HTML is already far more than the 8 000-character budget will keep.

A browser-ish User-Agent is set deliberately — the default httpx agent gets 403’d by a meaningful fraction of sites — while still identifying the bot honestly.

Every failure becomes one exception type

except httpx.HTTPStatusError as exc:
    raise FetchError(url, f"HTTP {exc.response.status_code}") from exc
except httpx.HTTPError as exc:
    raise FetchError(url, type(exc).__name__) from exc

404, connection refused, DNS failure, TLS error, timeout — all collapse to FetchError carrying the url and a short reason. The caller then needs exactly one except clause to implement “skip this URL, keep the pass alive.” Narrowing the exception surface at a boundary is what makes the degradation ladder in the next section readable.

Stage 3

Clean: HTML in, prose out

Raw HTML is mostly not content. clean_html is a deliberately small readability pass — no heavyweight dependency, three steps.

_NOISE_TAGS = ("script", "style", "noscript", "template", "svg",
               "nav", "footer", "header", "aside", "form")

soup = BeautifulSoup(html, "html.parser")
for tag in soup(list(_NOISE_TAGS)):
    tag.decompose()                      # 1. delete chrome outright
text = soup.get_text(separator="\n")     # 2. flatten to lines
return _normalize(text, max_chars=max_chars)   # 3. collapse + truncate

The tag list is the interesting part: nav, footer, header and aside are stripped not because they are invalid but because their text is the same on every page of a site. Leaving them in means every source from one domain shares a few hundred identical tokens, which both wastes budget and gives the extractor spurious repetition to latch onto.

Truncation prefers a word boundary, but only if one is close:

if last_space > max_chars * 0.8:   # only trim back if we're not losing much
    cut = cut[:last_space]
return cut.rstrip() + "…"

The 0.8 guard stops a pathological page — one long unbroken string, say minified JSON — from being cut back to almost nothing just to land on a space. The trailing ellipsis is a visible marker that a source was clipped.

Failing soft by design

clean_html returns "" for empty or unparseable input instead of raising. Combined with content = page["text"] or hit["snippet"], a page that parses to nothing degrades to its search snippet rather than producing an empty source.

The two text fields

snippet vs content

Both are text on the same RawSource, and they come from completely different places at completely different costs.

snippetcontent
Written bythe search enginethe page itself
SourceTavily’s content field, or DDG’s .result__snippethttpx GET → clean_html()
Costfree — arrives with the search responseone HTTP request, a semaphore slot, up to 8s
Sizea sentence or twoup to 8 000 characters
Relevancepicked for your querythe whole page, query-agnostic
Can it fail?no — if the search returned, it existsyes, constantly

The relationship between them is a single or:

page = await deps.fetcher.fetch(hit["url"])
content = page["text"] or hit["snippet"]      # empty page → snippet
# …and on FetchError:
content = hit["snippet"]                          # no page at all → snippet
A source where snippet == content is a degraded source

That equality is the tell that the fetch failed or the page cleaned to nothing. Both fields are stored precisely so the difference stays visible — had the node overwritten snippet, you could never tell a rich source from a fallback one when debugging a thin report.

Downstream they are used in opposite directions

ConsumerPreferenceWhy
_render.py — prompt blockscontent or snippetthe LLM wants as much real text as the budget allows
pack.py — chat retrieval bodycontent or snippetsame: rank and quote over full text
pack.py — citation displaysnippet or content[:200]a citation wants a short, query-relevant blurb, not a page dump

So content is the reasoning field and snippet is the display field, with each falling back to the other. Keeping both is what lets that split exist at all.

Bounded fan-out

Two gathers and one semaphore

The parallelism is nested, and only the inner layer is bounded.

# outer: every unresearched question at once
collected = await asyncio.gather(
    *[_research_question(q, errors) for q in todo]
)

# inner: the top 3 hits for one question at once
tasks = [_fetch_source(hit, errors) for hit in hits[:_FETCH_TOP_N]]
return list(await asyncio.gather(*tasks))

# the gate, shared by every fetch in the run
async with semaphore:
    page = await deps.fetcher.fetch(hit["url"])

asyncio.gather is Promise.all: start everything, wait for all of it, return results in argument order. asyncio.Semaphore(4) is a counter — async with takes a permit or suspends the coroutine until one frees up. Suspends, not blocks: the event loop keeps serving other requests while a fetch waits its turn.

Searches are not gated

The semaphore wraps only fetch. Search calls fan out one-per-question with no limit, so a ten-question plan fires ten concurrent search-API calls. Fine at current plan sizes and against Tavily’s quotas, but it is an unbounded fan-out on paper — and the first thing to notice if the planner is ever allowed to produce many more questions.

The semaphore is per-run, not global

It is created inside build_researcher(deps), which runs once per build_graph — and build_graph is called once per run in _invoke. So the limit of four is per workflow run. Two concurrent runs on one worker can have eight fetches in flight. A truly global cap would need the semaphore hoisted into WorkflowDeps.

Why the shared errors list is safe

errors: list[dict[str, Any]] = []
# mutated from many concurrent tasks…
errors.append({"node": "researcher", "url": hit["url"], "error": str(exc)})

No lock, and none needed. Every task runs on the same event loop thread, and list.append contains no await — so it cannot be interrupted part-way. This is the single-threaded-concurrency guarantee doing real work: you only need synchronisation around state that stays inconsistent across an await point.

Idempotence

De-duplication happens twice

Two different URL collisions are possible, and they are handled in two different places.

CollisionHandled byWhere
Two questions surface the same page in one passan explicit seen set in the noderesearcher.py
A later iteration re-finds a page from an earlier pass_merge_unique_sources, the channel reducerstate.py
# in-pass dedupe — the node's own responsibility
seen: set[str] = set()
for src in sources:
    if src["url"] in seen: continue
    seen.add(src["url"]); deduped.append(src)

The node cannot rely on the reducer alone, because the reducer merges the node’s return value into existing state — duplicates inside that single return would survive. And the reducer cannot be dropped either, because the node has no visibility of earlier iterations. Both layers are load-bearing.

Why URL is a good enough key

It is not perfect — tracking parameters and http vs https defeat it, and fetch follows redirects so the stored url may differ from the one searched. A stricter version would normalise the URL or hash the cleaned text. Naming that limitation is better than pretending the key is exact.

First pass only

The company-site crawl

Search finds what the world says about a company. It is unreliable at surfacing what the company says about itself, so iteration 0 also walks six fixed paths on the target domain:

_SITE_PATHS = ("", "/about", "/products", "/pricing", "/careers", "/blog")

if iteration == 0:
    sources.extend(await self._crawl_site(state["website"], errors))

Those paths are chosen for what a sales-research objective actually needs: positioning (/about), what they sell (/products), how they sell it (/pricing), where they are investing (/careers), and recent activity (/blog). It is a heuristic, not a crawler — no sitemap, no link following, no robots.txt handling.

This branch swallows errors on purpose

_crawl_site catches FetchError and returns None without recording anything — unlike the search path, which logs into state.errors. Most of these paths will 404 on any given site; recording six expected misses per run would drown the genuine failures. Silence is right here, and noise would be wrong.

The crawled pages get a synthesised title ("{website} /about") and their snippet is just the first 280 characters of their own text — there is no search engine in this path to supply one.

Degrade, don’t die

The fallback ladder

This node expects failure. There are four rungs, and only the last one fails the run.

1 · one URL won’t fetchFetchError caught → content = snippet, error logged → source still produced
↓
2 · the page cleans to nothingpage["text"] or hit["snippet"] → source still produced
↓
3 · a whole search failscaught per question, logged, returns [] → that question contributes nothing, the others continue
↓
4 · nothing at all, everraise → node_errored → run fails
# the only line in this node that can fail the run
if not deduped and not (state.get("raw_sources") or []):
    raise RuntimeError("Researcher gathered no sources (all searches/fetches failed).")
Read the second condition carefully

The run only dies if this pass produced nothing and no earlier pass did either. On a loop-back iteration that gathers zero new sources, the node returns quietly and the workflow proceeds to report on what it already has. A fruitless second pass is a disappointing report; a fruitless first pass is a report with no evidence at all, which is worse than an error.

This particular failure is deliberately not retried

The graph’s retry policy only fires on transient transport exceptions:

_TRANSIENT = (httpx.HTTPError, ConnectionError, TimeoutError, asyncio.TimeoutError)
def _retry_on(exc: Exception) -> bool:
    return isinstance(exc, _TRANSIENT)

A RuntimeError is not in that tuple, so “gathered nothing” fails immediately rather than burning two more full passes over the whole plan. The individual network failures underneath it were already retried three times each inside the search client.

The 5-versus-3 gap

Each search asks for five results and then fetches three. The other two hits are discarded entirely — not even kept as snippet-only sources, though they cost nothing extra to keep since the snippet already arrived. Two knobs that ought to be related are a setting and a hard-coded constant respectively, so they can drift. Cheap fix, good thing to have noticed.

Flashcards

Rapid-fire

What’s the difference between snippet and content?

snippet comes from the search engine and is free — a query-relevant sentence or two that always exists. content is the fetched page, cleaned and capped at 8 000 chars, and it can fail. On any fetch failure content falls back to snippet, so a source where the two are equal is a degraded source. The LLM prompts prefer content; citation display prefers snippet.

How do you stop the researcher hammering the network?

An asyncio.Semaphore(4) shared by every fetch in the run, including the site crawl. async with semaphore suspends the coroutine rather than blocking a thread, so waiting fetches cost nothing while other requests are served. Note the honest caveat: it bounds fetches only — searches fan out one per question, ungated.

Why doesn’t one dead URL fail the run?

Because failure is expected, so it degrades in tiers: a dead URL falls back to its snippet and records an entry in state.errors; a dead search drops that one question and returns []; only a pass that yields nothing and has no prior sources raises. That last condition matters — a fruitless second iteration still lets the workflow report on what it already gathered.

Why de-duplicate twice?

Different collisions. The seen set inside the node removes duplicates within one pass, which the reducer cannot see because it only merges the node’s return value into existing state. The _merge_unique_sources reducer removes duplicates across iterations, which the node cannot see because it has no view of prior state. Neither layer is redundant.

How do you avoid re-searching everything on the research loop?

researched_question_ids is an append-only reducer channel. Each pass filters the plan down to ids it has not seen, so a loop-back only chases the planner’s new gap-closing questions. It is also why the conditional edge routes back to the planner rather than the researcher — without new questions, todo would be empty and the pass would fetch nothing.

Why is a shared mutable errors list safe without a lock?

All the tasks run on one event-loop thread and list.append contains no await, so it cannot be suspended half-done. In asyncio you only need synchronisation around invariants that must hold across an await point — that is the whole difference from threading, where any bytecode boundary is a preemption point.

Why strip nav, header and footer specifically?

Their text is identical on every page of a site. Left in, every source from one domain shares hundreds of the same tokens — wasting the prompt budget and handing the signal extractor spurious repetition that looks like emphasis. Removing site chrome is as much about signal quality as size.

Why does the node depend on a Protocol instead of a client?

So the node depends on a capability, not a vendor. Tavily, DuckDuckGo and the test fake all satisfy SearchClient structurally — no inheritance — and swapping providers touches one factory function. It is the same dependency inversion as WorkflowDeps, and it is what lets the entire graph be tested with zero network.
